# Publication error safety and diagnostics

- HTTP helper now requires valid JSON even for HTTP 200. HTML 403 during a GET is treated as an edge/read failure, not proof the publication failed. Structured JSON 401/403 permission denials remain non-retryable. Error metadata includes phase, hostname, pathname (no query/credentials), HTTP status and response format.
- Bluesky verification and reply parent reads use a GET-only allowlisted fallback from cached public.api.bsky.app to direct api.bsky.app. No credentials are forwarded; publication POSTs never use this fallback. Source: https://bsky.network/docs/api-directory/ . Media staging may retry an HTML 403 up to three times; JSON access denials do not retry.
- Existing failed Bluesky/Tumblr social-verification tasks with external IDs resume read-only verification at startup and on Retry, preserving externalId/containerId. They never recreate a published record. Permanent verification errors after an ID exists become unknown rather than a safely retryable failed publish.
- Instagram ERROR is not enough to infer codec, connectivity or permissions. Read-only diagnose-publishing now reports ffprobe codec/dimensions/duration, current Meta container status and public/VPS/local Range responses. Bluesky failed rows report whether an external ID exists and compare both AppViews. No create/upload/publish request is made by diagnostics.
- QA mocks the external APIs; no production post/comment is sent. Backend health feature safeSocialVerification confirms rollout. Existing Instagram container/media needs VPS diagnostic output before a specific remedy is justified.
