# Device notification deduplication and deep links

Incoming messages have a dedicated push with the customer name and message preview. In-app message receipts, legacy comment receipts, and generic SLA overdue alerts must not generate a second device push for the same customer activity. SLA alerts remain in the app. Other actionable notifications use their actual title/body and route; preview privacy preferences remain respected.

Message pushes include the conversation and message IDs. Task pushes include the handoff ID. The service worker focuses an existing app first, asks it to handle the deep link, and navigates or opens a same-origin window if the app is outdated or the client is unavailable. The app refreshes authorized state before opening a notification target, preserves drafts, clears list search filters, opens the conversation/task, and highlights the target message when available. Cold start and post-login URLs retain the target until state is ready.

Validation: mocked push delivery confirms one message push despite accompanying receipt/SLA records; service worker VM tests cover focus ordering, rejected navigation, warm-app acknowledgement, and cross-origin rejection. Local browser tests cover cold deep links and warm navigation from a compact dashboard into full chat history. The full regression suite passed (596 tests), with an additional warm acknowledgement test passing afterward. No test messages were sent to customer devices. Actual Android notification tray/installed-app launching still needs confirmation on the user's phone.


Mobile follow-up: support both callback and Promise notification permission APIs, check PushManager permission separately when the Notification API reports a stale default, and never bypass an explicit denied site permission. An enabled device with granted permission can recreate a lost subscription; returning from OS settings refreshes its status. UI distinguishes website permission from Android app notification settings and retains unsaved preferences during status polling. Physical Android receipt still requires validation on the affected device.

Comment authors: Meta may omit `from` even when a Page token includes `pages_read_user_content`. Preserve known names, accept legacy webhook sender fields, and hydrate names from authorized detail responses without rewriting comment attachments or replaying notifications. Missing author counts are shown by channel. Do not infer names from comment IDs or scrape profiles. Publishing status tooltips prefer `remoteName` over a generic configured channel name.


Android follow-up: an explicit enable/test action records only bounded permission enums, platform class, standalone mode and a random local diagnostic ID; no push endpoint, keys, URL history or message content goes into diagnostics. Test notifications now carry a one-test identifier. After `showNotification` resolves, the worker uses the existing authenticated bootstrap CSRF flow to acknowledge it. Provider acceptance is shown separately from device processing; it does not prove an OS banner was visible. Sending a test refreshes/reconciles its subscription first. Explicit denied permission is never bypassed.
