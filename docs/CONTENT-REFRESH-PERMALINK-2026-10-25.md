# Content realtime and published permalink recovery

The screenshot's small `200 unchanged` state responses are successful checks, not failed publications. They were triggered too frequently because the global SSE stream emitted on unrelated workspace changes. The Content page now subscribes to a publishing-specific revision, and background refreshes coalesce with a five-second minimum interval and one request in flight. Dialogs, active text fields and hidden documents suppress these background reads. Explicit edits and navigation retain immediate refresh. Notification polling and chat realtime retain their own paths.

An Instagram/Threads publish can succeed and return a media ID while the subsequent permalink GET fails or the link is not yet available. Previously that empty URL was never repaired. Missing links now have a read-only recovery path by exact platform media ID, with request deduplication, an eight-second deadline, a one-minute initial retry increasing to one hour, and a bounded worker processing two missing receipts per minute. Clicking a missing destination also attempts recovery. Only official platform post URLs are accepted. Deletion/replacement races are rechecked before saving. Recovery cannot create a publication or repeat a publish request; it never changes a successful receipt into a failure.

The recovery endpoint requires content permission and access to the destination channel. No token or customer data is placed in frontend assets. `publicationPermalinkRecovery` in `/api/health` confirms the backend release. Android TWA uses the same Vercel frontend; the backend must also be updated on the VPS.

QA covers event bursts/slow requests, dialog suppression, retry backoff, concurrent link recovery, stale/deleted receipts, URL validation and unrelated chat writes not invalidating Content realtime. Production UI inspection remains unavailable after the browser approval gate reported exhausted workspace credits; no alternate browser mechanism was used.
